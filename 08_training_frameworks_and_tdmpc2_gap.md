# RL Training Frameworks, and What a Real TD-MPC2 Driving Integration Would Require

`02_rl_algorithms.md` covered *algorithms* (PPO, SAC, DQN, Dreamer, TD-MPC2) and flagged that TD-MPC2 lacks a mature driving-simulator integration. This file covers the *engineering layer one level down* — the training frameworks that actually wire an algorithm to an environment, how they pair with the simulators from `01`, and then gives the concrete, itemized engineering breakdown of what integrating TD-MPC2 with a driving simulator would actually involve, since that's the gap most directly relevant to your background.

## The framework landscape

| Framework | Maturity | Native driving integration | Multi-agent support | Learning curve | Best fit |
|---|---|---|---|---|---|
| **Stable-Baselines3 (SB3)** | Very high — the de facto standard for single-process, research-to-hobbyist RL | Excellent — highway-env registers with Gymnasium automatically, MetaDrive's own docs show direct SB3 `PPO`/`SubprocVecEnv` examples, CARLA via `gym-carla`/`CARLA-GymDrive` wrappers | None natively (single-agent only; PettingZoo wrappers exist for some envs but SB3 itself has no multi-agent core) | Low | Tier 1-2 (`06`), and honestly good enough for most of Tier 3's single-ego use cases too |
| **RLlib (Ray)** | High, but its API has churned significantly (the "new API stack" migration) — expect some version-pinning friction | Official CARLA tutorial exists ([`tuto_G_rllib_integration`](https://carla.readthedocs.io/en/latest/tuto_G_rllib_integration/)); `macad-gym` connects CARLA+RLlib+Gym explicitly for multi-agent scenarios | First-class — this is RLlib's actual differentiator, built for distributed multi-agent training from the ground up | Medium-high — config-object-heavy API, real distributed-systems concepts (rollout workers, learner actors) leak through | Multi-agent traffic (self-play, MARL per `02`), and any scenario needing many parallel environment instances across machines, not just processes |
| **CleanRL** | High code quality, single-file-per-algorithm philosophy | None built-in for any driving simulator — no CARLA/MetaDrive/highway-env example scripts ship with it | None | Low to read, medium to adapt (you're editing algorithm internals directly, not calling a black-box `.learn()`) | Best used as a *reference implementation to learn from or fork*, not a turnkey driving-RL tool — genuinely valuable if you want to understand exactly what SB3's PPO/SAC are doing under the hood before trusting them, or if you want to hand-modify an algorithm (e.g., add a custom auxiliary loss) without fighting SB3's abstraction layers |
| **Tianshou** | Solid, PyTorch-based, modular internals | No dedicated driving-simulator wrapper found, but used directly in the **Driver Dojo** generalization-benchmark paper (`05`) to test PPO/SAC/etc. against its randomized-scenario suite, and has native PettingZoo support | Via PettingZoo integration | Medium | A reasonable SB3 alternative specifically if you want easier access to its internals for research-style algorithm modification, or if you're already using Driver Dojo |

A rough empirical note worth internalizing before picking one on "which framework is fastest" grounds: a controlled comparison study found SB3, CleanRL, and the original OpenAI Baselines land roughly on par with each other in PPO implementation quality (about 50% of runs hitting superhuman reference performance in the benchmarked tasks), while RLlib and Tianshou showed meaningfully lower hit rates (under 15%) in that same comparison — a reminder that "more scalable/more features" and "matches the reference algorithm's published performance out of the box" are not the same axis, and it's worth validating any framework against a known simple task before trusting it on a driving environment.

**Practical recommendation, tying back to `06`'s tiers**: SB3 for Tier 1 and almost all of Tier 2 — the ecosystem depth (rl-baselines3-zoo pretrained agents and hyperparameters, per `07`) outweighs anything RLlib or Tianshou offer at this scale. Reach for RLlib specifically once you need either (a) genuinely distributed rollout collection across multiple machines, or (b) native multi-agent training where other cars are themselves learning policies (Tier 3 MARL scenarios, `02`'s self-play discussion). CleanRL is the right tool only when the goal shifts from "train a good policy" to "understand or modify an algorithm's internals" — treat it as a reading resource more than a project dependency.

Sources: [RLlib CARLA integration tutorial](https://carla.readthedocs.io/en/latest/tuto_G_rllib_integration/), [macad-gym](https://github.com/praveen-palanisamy/macad-gym), [MetaDrive training docs](https://metadrive-simulator.readthedocs.io/en/latest/training.html), [CleanRL](https://github.com/vwxyzjn/cleanrl), [Driver Dojo (2207.11432)](https://arxiv.org/pdf/2207.11432), [On the Mistaken Assumption of Interchangeable DRL Implementations (2503.22575)](https://arxiv.org/html/2503.22575v2), [Tianshou GitHub](https://github.com/thu-ml/tianshou).

## What a real TD-MPC2 driving integration would concretely require

`02_rl_algorithms.md` already noted TD-MPC2 has no off-the-shelf driving integration comparable to CarDreamer for the Dreamer family. This section extends that into an actual itemized engineering breakdown, based on directly reading TD-MPC2's own environment-registration code (`nicklashansen/tdmpc2`, `tdmpc2/envs/__init__.py`).

**How TD-MPC2 currently onboards a new environment.** The reference codebase uses a factory pattern: `make_env(cfg)` tries a sequence of specialized makers (`make_dm_control_env`, `make_maniskill_env`, `make_metaworld_env`, `make_myosuite_env`, `make_mujoco_env`), each of which either successfully constructs the environment or raises `ValueError` so the next maker is tried. Whatever environment comes back must expose:
- an `observation_space` that is either a single `Box` or a `Dict` of named component spaces,
- an `action_space` that is a `Box`, with `env.action_space.shape[0]` giving the action dimensionality,
- a `max_episode_steps` attribute.

From this, the framework auto-derives `cfg.obs_shape` (a dict of observation-name → shape), `cfg.action_dim`, `cfg.episode_length`, and `cfg.seed_steps` (minimum 1000, or 5× episode length) — then wraps the environment in a `TensorWrapper` (single-task) or `MultitaskWrapper` (multi-task) to standardize tensor I/O across the different backends.

**Item-by-item, what this means for a driving simulator:**

1. **A new `make_*_env` branch, plus registration.** There is no `make_highway_env` or `make_carla_env` or `make_metadrive_env` in the reference codebase — you'd write one from scratch, following the existing makers as a template. This part is genuinely the easy part; it's boilerplate once you understand the pattern.

2. **Action space: the good news.** MetaDrive's default continuous `[steer, accel]` action space and highway-env's continuous action mode are already `Box` spaces — a direct match to what TD-MPC2 expects, no adapter needed. Highway-env's **discrete** meta-actions (`LANE_LEFT/IDLE/LANE_RIGHT/FASTER/SLOWER`, per `03`) are *not* a match — TD-MPC2 is built end-to-end for continuous control (its planner does gradient-based/CEM-style trajectory optimization over a continuous action space), so a discrete or hybrid parameterized action space (per `03`'s action-space axis) would require either abandoning discrete actions entirely or building genuinely new planner-side logic that doesn't exist in the reference implementation — this is a real, non-trivial research problem, not just a wrapper.

3. **Observation space: partially matches, partially doesn't.** MetaDrive's default vector+LiDAR-distance observation and highway-env's Kinematics vector are both flat arrays — trivially expressible as a `Box`, matching TD-MPC2's simplest case. Camera/BEV image observations (CARLA, or MetaDrive's optional first-person mode) are supported *in principle* — TD-MPC2's codebase does support pixel observations for DMControl tasks via an `obs=rgb` argument — but the visual encoder architecture shipped with TD-MPC2 was tuned against DMControl's small (typically 84×84) pixel tasks and ManiSkill's manipulation-scene renders, not against driving-scale scenes (wider field of view, more scene complexity, BEV rasters at different resolutions). Expect to need real architecture/hyperparameter tuning here, not a drop-in reuse.

4. **Episode length: a structural mismatch worth flagging explicitly.** TD-MPC2 wants a fixed `max_episode_steps` known up front, and its planner reasons over a fixed short horizon each step. Driving episodes are naturally *variable*-length (a route completes early, or a collision terminates the episode early, or a timeout caps it) — this is a real mismatch with the "fixed episode length" assumption baked into the reference config-derivation code, though it's a solvable one: you'd cap at a `max_episode_steps` ceiling (as MetaDrive/highway-env already do) and rely on TD-MPC2's own learned termination/discount signal to handle early collision-terminated episodes, which is architecturally supported but not something any existing driving integration has actually validated in practice.

5. **Reward scale.** TD-MPC2's default hyperparameters (including its SimNorm normalization and loss weighting) were tuned against DMControl/Meta-World/ManiSkill reward scales. Whatever reward function you design per `04_reward_design.md` will very likely need its own scale/normalization pass before TD-MPC2's default hyperparameters behave sensibly — this is normal engineering friction for *any* new domain with any RL algorithm, but worth budgeting for explicitly rather than assuming the published hyperparameters transfer.

6. **Planning-time latency vs. environment step cost — a subtle but real throughput concern.** TD-MPC2's core value proposition is doing MPC-style planning (multiple forward passes through the learned dynamics model, evaluating a short rollout horizon) *at every environment step*. In CARLA, where a single environment step is already expensive (rendering-bound), this planning overhead is comparatively cheap and the model-based sample-efficiency argument holds cleanly. In highway-env or MetaDrive, whose entire appeal is thousands-of-FPS lightweight simulation, TD-MPC2's per-step planning overhead could plausibly become the throughput bottleneck instead of the environment itself — meaning the "let the world model absorb most of the sample cost" argument (central to `02`'s case for model-based RL in driving) is *weakest* exactly in the environments that are otherwise the easiest and cheapest to integrate with. This tradeoff doesn't appear to have been directly measured in any published driving-specific TD-MPC2 work found in this research pass — it's a genuine open question you'd be answering yourself.

7. **No multi-agent story at all.** TD-MPC2 is purely single-agent by design. If your traffic includes scripted NPCs (the default and easiest case per `03`), this is a non-issue — exactly as any single-agent algorithm treats MetaDrive's or highway-env's scripted vehicles as part of the environment's dynamics, not as separate agents to coordinate with. If you want *learning* traffic (multi-agent RL, per `02`), TD-MPC2 offers nothing here — you'd need either a from-scratch multi-agent extension (a real research undertaking) or to keep TD-MPC2 confined to the single ego-agent role while other cars stay scripted or offline-data-driven.

**Rough engineering-effort estimate.** Getting a *working* (not necessarily good) TD-MPC2 + highway-env integration — continuous action space, flat-vector observation, fixed episode-length cap, reward rescaled — is plausibly a 1-3 week effort for someone who already understands both TD-MPC2's codebase and the target environment, since the action/observation space shapes already line up with `Box`/`Box`. A TD-MPC2 + CARLA integration is meaningfully harder — likely weeks to a couple of months — because of the compounding pixel-observation encoder work, variable-episode-length handling, and the planning-latency-vs-rendering-cost tradeoff above, none of which has a published reference to build from. As of this research pass, the closest thing that exists to validating any of this is the blog-level [Driving With Imagination](https://satyamcser.substack.com/p/driving-with-imagination-dreamerv3) comparison (exploratory, not a maintained repo or peer-reviewed benchmark) — meaning whichever direction you take this, you would genuinely be producing new public information rather than reproducing an existing result.
